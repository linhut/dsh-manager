## 一、体系全景

模型选择配置横跨 **4 层 6 个文件**：

| 层 | 模块 | 职责 |
|---|---|---|
| ① GUI 渲染层 | `src/assets/js/modules/model-config.js` | 配置档案（profile）CRUD、一键应用到 4 个外部工具、备份/还原、导入导出 |
| ① GUI 渲染层 | `src/assets/js/app.js` | LLM 提供商表单、LLM 能力路由 UI、AI 生图页、模型拉取与容量录入 |
| ② IPC 桥接层 | `electron/preload.cjs` + `electron/ipc-handlers.js` | 所有 `mcc:*` / `config:llm-*` / `llm-routing:*` / `llm:fetch-models` 通道；密钥脱敏、SSRF 防护、启动时自动迁移 |
| ③ 核心逻辑层 | `packages/core/src/model-config-center.js` | 档案中心（明文密钥落盘 `~/.dsh/manager/model-config-center.json`）+ 4 个工具适配器 |
| ③ 核心逻辑层 | `packages/core/src/config.js` | DSH 提供商保存/迁移/清洗、能力路由读写、能力识别、知名模型规格表、密钥安全 |
| ③ 核心逻辑层 | `packages/core/src/capability-router.js` + `packages/plugins/dsh-capability-router/lib/index.js` | 能力路由插件：安装器（Manager 侧）与运行时（DSH 内 Cordis Service） |
| ③ 核心逻辑层 | `packages/core/src/imagegen.js` | AI 生图：从 `llm-*` 段解析 provider/apiKey 调 `/images/generations` |
| ④ 落点 | `~/.dsh/settings.yaml` / `.credentials.yaml` / `~/.dsh/manager/*` / 外部工具配置文件 | 最终写入目标 |

**配置存储形态**（settings.yaml 相关段）：

```
settings.yaml
├── llm-pi-ai.providers.<name>   # DSH 官方通用适配器（唯一真正被 DSH 读取的段）
├── llm-deepseek                 # DSH 官方平铺单段（仅 DeepSeek）
├── llm.<name>                   # 旧 Manager 格式（alpha4 不读，写入时自动迁移/清除）
├── llm-openai-compatible 等     # 历史错误命名空间（启动时自动迁移到 llm-pi-ai）
├── capability-router            # 能力路由配置（DSH 插件热加载段）
├── manager.llm-routing          # 能力路由旧版兼容回退段（与上者双写）
├── agent-default-model          # 能力路由「设为默认」的落点（DSH 新建会话读取）
└── agent-presets                # Agent 预设（不直接含模型参数，引用 preset.yml/agent.cordis.yml）
.credentials.yaml                # 凭据引用名 → 密钥值（settings 内绝不落明文）
```

## 二、模型列表与分类

### 2.1 模型来源（三个来源，优先级从高到低）

1. **API 实拉**（`llm:fetch-models`，ipc-handlers.js）：请求 `{base}/v1/models` 或 `{base}/models`，逐个模型计算能力标签与容量规格。有 SSRF 防护（回环地址仅放行 ollama 默认端口 11434；禁 URL 内嵌凭据）。
2. **内置知名规格表**（`config.js → lookupModelSpec`）：约 25 条精确/前缀匹配（deepseek-v4-flash 1M/384K、gpt-4o 128K、claude-opus-4 200K 等）。仅当 API 元数据缺失时兜底补 `contextWindow/maxTokens`。
3. **用户手填**：表单直接填模型名；档案可 `testConnection` 后自动填首个模型。

### 2.2 能力分类（模型 → 能力）

`config.js → detectModelCapabilities(id, meta)` 输出能力数组，与能力路由五类对齐：

| 能力 key | 中文名 | 识别依据（名称启发式 + API 元数据 `input_types/input/modalities/capabilities`） |
|---|---|---|
| `semantic` | 语义理解 | 恒有（兜底能力） |
| `vision` | 识图 | 名含 vision/visual/-vl/4v/5v/omni/-4o/gemini/llava/minicpm/internvl；或元数据 input 含 image |
| `multimodal` | 多模态（补充型） | 元数据 modalities 声明，或名含 audio/voice/omni |
| `code` | 代码 | 名含 -coder/codex/deepseek-coder/qwen2.5-coder；或元数据 capabilities 含 code |
| `image` | 生图 | 名含 dall-e/flux/sdxl/stable-diffusion/draw/t2i；或元数据含 gen/draw/paint |
| `embedding` | 嵌入 | 名含 embedding/-embed/bge/m3e |

> ⚠️ 注意规避误判：`deepseek-v4-flash` 中的 "v4" 是版本号，`/(^|[-\d])[45]v($|[-_])/` 模式不会误判为视觉（有专门测试用例）。

### 2.3 视觉启发式（isVisionModelName）

**存在两处几乎重复的实现**：
- `config.js → DSHConfig.isVisionModelName`（静态方法，核心层）
- `app.js → isVisionModelName`（渲染层 window 函数，多出 `qwen2-vl/qwen-vl/glm-4v/glm-5v` 显式分支）

两处需**手工同步维护**，存在规则漂移风险（详见 §六 问题 1）。

## 三、参数配置项清单（用途 / 默认值 / 取值范围 / 优先级）

### 3.1 配置档案（profile）字段 — `model-config-center.js`

| 字段 | 用途 | 默认 | 取值/校验 | 应用优先级 |
|---|---|---|---|---|
| `name` | 档案名（双向联动：与 DSH 提供商同名视为已注册） | — | 必填非空 | — |
| `baseUrl` | API 地址 | — | 必填；应用时 strip 尾部 `/` | — |
| `apiKey` | 密钥（明文仅存 `~/.dsh/manager/`） | — | 编辑留空保留原值；含 `****` 视为占位 | **明文优先于 env** |
| `apiKeyEnv` | 环境变量引用名 | — | 如 `MY_API_KEY` | 无明文时使用；AtomCode 写为 `$VAR` |
| `model` | 主模型 | — | 必填非空 | — |
| `smallModel` | 快速模型（仅 Claude Code 使用 → `ANTHROPIC_SMALL_FAST_MODEL`） | 空 | 可选 | 仅 CC |
| `vendor` | 供应商名（仅 WorkBuddy 使用 → `models[].vendor`） | 空 | 可选 | 仅 WB |
| `contextWindow` | 上下文窗口 | 0（不写） | 正整数，可入 `128K/1M`（见 normalizeModelCapacity） | WB → `maxInputTokens` |
| `maxTokens` | 最大输出 | 0（不写） | 正整数 | WB → `maxOutputTokens` |
| `temperature` | 温度 | 空（不写） | 0–2，step 0.1 | **仅 WorkBuddy** → `models[].temperature` |
| `supportsVision` | 支持视觉 | false | bool | 全工具（AtomCode `supports_vision`、WB `supportsImages`、DSH `input:['text','image']`） |
| `supportsToolCall` | 支持工具调用 | true（表单 `!p || !== false`） | bool | **仅 WorkBuddy** → `supportsToolCall` |
| `setDefault` | 应用时设为默认 | false | bool | AtomCode → default_provider/default_model；WB → availableModels 覆盖 |

### 3.2 DSH LLM 提供商字段 — `config.js saveLLMProvider` 写入 `llm-<adapter>.providers.<name>`

| 字段 | 说明 | 默认 |
|---|---|---|
| `api` | 线路协议 | `openai-completions`；anthropic/claude 归一为 `anthropic-messages`（LLM_API_MAP） |
| `baseURL` | **必填**，空值直接抛错（DSH `resolveProfiles` 会拒绝整段） | — |
| `models[]` | `{id, name?, input?, contextWindow?, maxTokens?}`；`input` 缺省时按 `isVisionModelName` 补 `['text','image']`；容量需为正整数，非法值剔除 | `[{id: config.model}]` |
| `apiKeyEnv` | 凭据引用名（值存 `.credentials.yaml`）；空则省略字段（`credentialRef("")` 会让 DSH 抛 TypeError 拒绝整段） | 省略 |

**密钥优先级**（saveLLMProvider 内）：显式明文新 key > `env:` 前缀引用 > `apiKeyEnv` 引用 > 历史明文迁移 > 历史引用。

### 3.3 能力路由 — `capability-router` / `manager.llm-routing`（双写）

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | true | 路由总开关 |
| `defaultCapability` | `semantic` | 内容检测未命中（vision/code）时回退的能力 |
| `capabilities.<cap>` | 空 | `{provider: <providerKey>, model: <modelId>}`；provider 必须真实存在于 `llm-*.providers` |

附加落点：`applyDefaultModel(cap)` → 写 `agent-default-model: {provider, model}`（仅新建会话生效）。

### 3.4 “强度”与采样策略的现状

- **强度（reasoning effort）**：DSH 的 `vendor-patches/dsh-llm@0.1.2-rc.1` 中定义了 `reasoningEffort` 请求级语义（`UNSUPPORTED_REASONING_EFFORT` 校验），能力路由插件切换模型时会**删除** `reasoningEffort`；但 **Manager 的表单/档案/能力路由 UI 均未暴露该参数** — 用户无法在配置层设置“强度”。
- **采样策略**：仅档案提供 `temperature`（且只有 WorkBuddy 生效）；**无 top_p / top_k / frequency_penalty / presence_penalty**。
- DSH 请求级默认有 `temperature/maxTokens` 语义（vendor patch），Manager 层未建模。

## 四、配置加载与校验逻辑

### 4.1 加载路径

| 时机 | 动作 |
|---|---|
| IPC 请求时 | `config.js read()` 解析 settings.yaml + .credentials.yaml（两个文件独立存在，缺一不短路） |
| **应用启动时** | `ipc-handlers.js` 启动钩子 → `new DSHConfig().migrateLLMProviders()`（失败仅告警不阻塞启动） |
| 打开 LLM 设置页 | 再次 `migrateLLMProviders()` 幂等执行 |
| 能力路由 UI 加载 | `getLLMRouting()` 优先读 `capability-router` 段，缺失回退 `manager.llm-routing` |

### 4.2 校验/清洗要点

1. **迁移与归一化**（migrateLLMProviders）：`llm-openai* / llm-anthropic / llm-ollama / llm-google / llm-azure / llm-custom / llm-claude` 等历史错误段 → 搬迁到 `llm-pi-ai.providers`；同时就地清洗：删除空 `apiKeyEnv`（防 credentialRef("") 抛错）、删除 `provider` 字段（pi-ai `rejectRemovedFields` 拒绝）、剔除空 `baseURL` 条目、归一化 `models`。
2. **密钥安全**：
   - 保存时明文进 `.credentials.yaml`，settings 只存引用名；
   - 下发渲染层时 `sanitizeSettingsForRenderer` 把历史明文替换为 `apiKeyConfigured` 布尔位；
   - 写回时 `_preserveLegacyPlainKeysOnWrite` 从磁盘回填原明文，防止“静默删除”；`_stripRendererOnlyFields` 剥离 UI 状态位。
3. **容量校验**：`normalizeModelCapacity`（核心）接受正整数与 `128K/1M` 字符串；`parseCapacityInput`（渲染层）同名逻辑；非法值在保存前被拦截。
4. **连通性检测**：`testConnection` 请求 `/models` 端点，8s 超时，自动填首个模型；`llm:fetch-models` 15s 超时 + SSRF 防护。
5. **应用前校验**：`saveProfile` 必填（名称/地址/模型）；`apply` 校验档案存在与工具 id 支持；`applyDefaultModel/resolveCapability` 校验 provider/model 真实存在。

## 五、跨工具应用与调用关系

### 5.1 四个外部工具适配器（model-config-center.js）

| 工具 | 配置文件 | 写入内容 | 状态检测 |
|---|---|---|---|
| AtomCode | `~/.atomcode/config.toml` | 段落级 upsert：`provider_accounts.<id>`（provider/openai-compatible、api_key、base_url）+ `models."<id>/<model>"`（account、supports_vision、context_window、max_tokens）；setDefault 时写 `default_provider/default_model` | 解析 TOML 段首模型反查档案（baseUrl+model 匹配，须已配密钥） |
| Claude Code | `~/.claude/settings.json` | env 块合并：`ANTHROPIC_BASE_URL/AUTH_TOKEN/MODEL/SMALL_FAST_MODEL/CUSTOM_MODEL_OPTION` | 读 env 四键反查 |
| WorkBuddy | `~/.codebuddy/models.json` | `models[]` 按 id 合并：`{id,name,vendor,apiKey,maxInputTokens,maxOutputTokens,url,temperature,supportsToolCall,supportsImages}`；setDefault → `availableModels=[id]` | 取 models[0] 反查 |
| Codex CLI | `~/.codex/config.toml` + `auth.json` | config.toml 顶层 `model`/`model_provider` + `model_providers.<id>` 段；auth.json 写 `OPENAI_API_KEY`（有明文才写） | 解析 config.toml 反查 |

写入前自动备份到 `~/.dsh/manager/backups/model-config-center/`（每工具保留 10 份），支持一键还原。

### 5.2 调用关系（单向依赖链）

```
GUI(model-config.js / app.js)
   │  window.dshManager.*
   ▼
preload.cjs ──► ipc-handlers.js
   │  mcc:* 通道               │ config:llm-* / llm-routing:* / llm:fetch-models
   ▼                          ▼
ModelConfigCenter        DSHConfig(config.js)
   │  apply()                 │  write settings.yaml / credentials
   ▼                          ▼
外部工具配置文件          ~/.dsh/settings.yaml
                                    │ DSH 启动读取
                                    ▼
                        dsh-capability-router 插件（DSH 内运行时）
                                    │ 读取 capability-router 段
                                    ▼
                        每次请求按内容切换 provider/model（并删 reasoningEffort）
```

**双向联动**：档案与 DSH 提供商同名即显示“已注册”；`mccWriteProviderToDSH` 可把档案写为 `llm-pi-ai.providers.<name>`（provider: pi-ai）；LLM 提供商表单勾选“同步为档案”可反向建档并一键应用。

## 六、问题识别：重复 / 冲突 / 缺失

### 6.1 重复（冗余实现，维护成本）

| # | 位置 | 说明 |
|---|---|---|
| D1 | `isVisionModelName`：config.js静态方法 vs app.js window 函数 | 逻辑几乎一致但实现不同（app.js 多 qwen2-vl/glm-4v/glm-5v 分支），漂移风险高 |
| D2 | 容量解析：`normalizeModelCapacity`（核心）vs `parseCapacityInput`（渲染层） | 两套 `K=1024/M=1024²` 正则，前者的 `1.5m` 后缀规则与后者一致但代码独立 |
| D3 | 能力标签：app.js `CAP_LABELS` vs 插件 `CAPABILITY_LABELS` | 同一个能力→中文名映射在渲染层与 DSH 插件各一份 |
| D4 | 能力列表：前端 `LLM_CAPABILITIES`（5 项） vs 插件运行时实际处理（仅 vision/code + image 回退 semantic） | embedding 仅“可配置”无运行时路径；UI 5 行 vs 实现 2 行 |
| D5 | 能力路由双写：`settings.capability-router` + `settings.manager.llm-routing` | 兼容旧版刻意为之，但造成 settings.yaml 数据冗余、两处需保持同步 |
| D6 | 容量默认值：WorkBuddy 适配器硬编码 `maxInputTokens=200000 / maxOutputTokens=8192` | 与 `lookupModelSpec` 规格表（如 deepseek-v4-flash 1M/384K）不联动，用户不填容量时拿到的是通用默认值而非模型真实规格 |
| D7 | 同一模型数据两个录入入口（LLM 提供商表单 ↔ 档案表单） | 同名覆盖有 UI 提示但无一致化约束 |

### 6.2 冲突（语义不一致）

| # | 冲突点 | 详情 |
|---|---|---|
| C1 | apiKey 与 apiKeyEnv 优先级两套逻辑 | 档案侧：明文 > env；DSH 提供商侧：明文 > env:引用 > apiKeyEnv > 历史明文 > 历史引用。规则分散在 3 处（saveProfile / saveLLMProvider / _applyClaudeCode） |
| C2 | `supportsToolCall` 语义分裂 | 表单默认 true；WorkBuddy 用 `!== false`；但 `mccWriteProviderToDSH` 写 DSH 时**未传递**该字段（pi-ai 只写了 input）——同档案在不同工具生效范围不同 |
| C3 | temperature 仅 WorkBuddy 生效 | 表单标注“可选”，用户易误解为全局采样参数；AtomCode/Claude Code/Codex 均不写 |
| C4 | smallModel 仅 Claude Code 生效 | 其它工具忽略，属有意设计但 UI 无提示 |
| C5 | 能力路由 provider 语义 | UI 下拉展示 `providerKey (adapter)`，但写 DSH 是 providerKey；`agent-default-model.provider` 也是 providerKey —— 两处命名易混（测试用例注释亦指出） |

### 6.3 缺失

| # | 缺失项 | 影响 |
|---|---|---|
| M1 | **强度（reasoningEffort）无任何配置入口** | 用户无法配置推理强度；能力路由还会在切换时删除它（切换即丢失原强度） |
| M2 | **采样策略不完整**：仅 temperature，无 top_p/top_k/penalty | DSH 请求层有语义但 Manager 配置层缺失 |
| M3 | 能力路由运行时仅实现 vision/code 自动切换，embedding/image 无运行时路径 | UI 可配置 ≠ 运行时生效（image 有版本限制提示，embedding 未提示） |
| M4 | 模型容量规格表（lookupModelSpec）收录 25 条，更新需人工维护；手填模型无规格提示 | 过期风险；新模型（如 qwen3/glm-5）需手动补充 |
| M5 | 生图尺寸硬编码三档（1024x1024/1792x1024/1024x1792） | 非 OpenAI 兼容生图服务尺寸不支持时无自定义入口 |
| M6 | pi-ai 其它 DSH 支持字段（`wire_api` 等）未暴露 | Codex 用了 wire_api，DSH 侧未见对应配置入口 |
| M7 | 迁移类测试缺失 | 已有 credentials-migration / llm-routing / model-capabilities / model-config-center 测试，但 `saveLLMProvider` 的密钥迁移/命名空间迁移路径无独立测试 |

## 七、优化建议（按优先级）

### P0 — 正确性

1. **统一 `isVisionModelName`**：抽取 config.js 静态方法为唯一实现，app.js 改为 import/复用；git grep 确认无第三处。
2. **修复 supportsToolCall 传递**：`mccWriteProviderToDSH` 写入 pi-ai 时补充 tool 声明（或明确标注“仅 WorkBuddy 生效”），消除同档案跨工具语义分裂。
3. **能力路由切模型时保留/可配 reasoningEffort**：把 `delete withoutEffort.reasoningEffort` 改为“读取目标 provider/model 的已配置强度后重写”，避免切换丢掉强度。

### P1 — 一致性

4. **单选或合并录入入口**：LLM 提供商表单的“同步为档案”已是桥，可进一步把档案作为唯一数据源，提供商改为档案派生视图。
5. **容量默认值联动规格表**：`_applyWorkBuddy` 中 `200000/8192` 改为「档案容量 → lookupModelSpec(档案.model) → 兜底默认值」三级回退。
6. **能力路由 UI 与运行时对齐**：embedding 行加“仅配置、无运行时路径”提示（同 image 行）；或扩展插件支持 embedding。

### P2 — 补全

7. **参数面板扩展**：档案表单增加 reasonEffort 与 top_p（映射到各工具支持的形式，不支持的工具栏下划线提示）。
8. **规格表外置**：把 lookupModelSpec 的 KNOWN 表提取为 `models-spec.json`（受管数据文件），便于更新与测试。
9. **补迁移测试**：为 saveLLMProvider 的密钥优先级链路与 migrateLLMProviders 的错误段搬迁写单元测试（现有 4 个测试文件已覆盖了分支，唯独缺 migrate 主链路）。
10. **生图尺寸可配置**：尺寸下拉改为“预设 + 自定义”，后端透传。

### 附：推荐的结构收敛方向

若后续重构，建议把模型配置收敛为**单一数据源 + 适配器投影**：

```
ModelSpec(唯一模型规格来源：lookupModelSpec + API 元数据合并)
```

## 附录 B：能力路由插件运行时语义备忘

- 读取 `settings.capability-router`（Manager 写入，插件热加载）。
- 每请求检测最近一条 user 消息：含图片块 → `vision`；代码特征（围栏/扩展名/≥2 关键词）→ `code`；否则 → `defaultCapability`。
- `image` 作为默认能力时回退 `semantic`（DSH 当前不支持图片输出）。
- 未配置的能力/provider 未注册/已是目标模型 → 原样透传（绝不阻断请求）。
- 实时日志 `~/.dsh/manager/capability-router.log`，Manager UI 可读。
